## Context

See `proposal.md` for motivation. The current Hermes target (`src/installer/targets/hermes.ts`) configures `mcp_servers.codegraph` and enables `mcp-codegraph`, so Hermes can discover CodeGraph MCP tools after a new session. The gap is a guided Hermes-facing workflow that helps the agent choose the right graph operation, pass `projectPath` when needed, and preserve CodeGraph notices in the answer.

Relevant current implementation points:

- `src/installer/targets/hermes.ts` writes Hermes config for the MCP server/toolset.
- `src/mcp/tools.ts` exposes `ToolHandler`, tool definitions, project-path resolution, staleness/worktree notices, and handlers such as search/context/trace/callers/callees/impact/files.
- `src/bin/codegraph.ts` exposes CLI commands that mirror user-facing query and exploration operations.

## Goals / Non-Goals

**Goals:**

- Add a Hermes-facing wrapper asset/workflow that converts natural-language codebase questions into appropriate CodeGraph operations.
- Keep the wrapper thin: it should orchestrate existing CodeGraph MCP/CLI capabilities rather than creating a second query engine.
- Make project-path recovery explicit for Telegram/CLI/Hermes sessions that start outside the indexed repo.
- Preserve staleness, worktree, and not-initialized notices.
- Add automated verification for the generated Hermes integration artifact and at least one fixture-level wrapper behavior.

**Non-Goals:**

- Changing existing MCP tool schemas.
- Replacing `ToolHandler` or the CodeGraph query engine.
- Adding network-backed or hosted search.
- Supporting non-Hermes agent targets in this change.

## Decisions

### Decision 1: Implement the wrapper as a Hermes integration asset generated by the Hermes installer target

The wrapper should be emitted by the existing Hermes target alongside config instructions/assets, because the feature is Hermes-specific and should travel with `codegraph install` / installer behavior.

Alternatives considered:

- **Global core tool in Hermes**: rejected because CodeGraph already exposes MCP tools and Hermes core should stay narrow.
- **New CodeGraph CLI command only**: useful for humans, but it does not give Hermes an instruction surface for selecting graph operations.
- **Documentation only**: insufficient because agents need a repeatable, installed workflow prompt/asset.

### Decision 2: Route to existing MCP tools first, with CLI fallback only for verification or environments without MCP

The wrapper should prefer the MCP tools that Hermes discovers from `mcp-codegraph`, because those are the live integration surface. CLI commands remain useful for test fixtures, docs, and manual fallback.

Alternatives considered:

- **Always shell out to `codegraph query`**: simpler, but bypasses richer MCP tools such as context, trace, impact, and structured projectPath handling.
- **Directly import CodeGraph internals from Hermes**: rejected because it couples Hermes runtime assets to CodeGraph internals and Node module resolution.

### Decision 3: Preserve operational notices verbatim or near-verbatim

The wrapper should not summarize away CodeGraph's staleness, worktree mismatch, or not-initialized notices. These warnings are part of answer correctness and help the user fix environment issues.

Alternatives considered:

- **Return only the answer**: rejected because it can make stale or wrong-index answers look authoritative.

## Risks / Trade-offs

- [Risk] Generated Hermes assets drift from MCP tool names or behavior → Mitigation: test generated assets against the current tool list/expected tool names and keep the wrapper wording generic enough to survive small description changes.
- [Risk] Wrapper becomes too prescriptive and blocks valid exploration paths → Mitigation: describe routing preferences and fallbacks rather than a rigid one-command mapping.
- [Risk] Project-local vs global Hermes setup confuses users → Mitigation: include explicit `projectPath` recovery instructions and a verification path in docs/tests.
- [Risk] Installer writes user config unexpectedly → Mitigation: keep existing installer safety behavior; wrapper asset generation should be inspectable and covered by tests.

## Migration Plan

1. Add the wrapper asset/template and wire it into the Hermes target output.
2. Add tests that verify Hermes installation includes the wrapper and preserves existing config behavior.
3. Add fixture or snapshot-style validation for routing guidance, projectPath recovery, and operational notices.
4. Build and run the existing Vitest suite relevant to installer and MCP tooling.
5. Document how Hermes users invoke the wrapper after starting a new Hermes session.

Rollback: remove the generated wrapper asset from the Hermes target while leaving the existing `mcp_servers.codegraph` config path unchanged.
